# dsh-pocket 安全改造设计讨论

【最后更新时间】2026-08-31

## 目标

- 基于已有插件[shaobeichen/dsh-pocket](https://github.com/shaobeichen/dsh-pocket)改造一个安全优先的手机公网访问DSH的新插件。
- 同一部手机可以绑定任意设备（比如访问公司电脑和家里电脑上的 DSH）
- 公司内外统一通过固定 HTTPS 入口访问，不再同时维护局域网与公网两套入口。
- 入口只允许由对应宿主电脑本机批准过的手机凭据访问。
- 首次验证可以严格；验证完成后的日常使用应尽量方便。
- 安全方案应集成到 dsh-pocket，保持代码和长期维护简单可靠。
- 改造应具备通用性，完成后考虑向 dsh-pocket 上游提交 PR，使其他用户也能使用；不得硬编码用户自己的账号、域名、设备或基础设施。
- 暂不把公司网络监控作为方案约束；公司当前没有明确的相关监管限制。

## 用户使用流程

1. 用户在电脑上安装插件，并配置一个固定 Cloudflare 网址；插件不获取 Cloudflare 账号密码。
2. 用户只能在电脑本机发起“添加设备”，电脑显示短时、一次性的配对二维码。
3. 手机扫码并完成指纹、面容或锁屏密码确认，填写设备名称，再由电脑端人工批准。
4. 获准手机以后通过该电脑的固定网址访问；每次关闭页面后重新进入，都再次进行手机本机确认。
5. 页面持续打开和使用时不重复打扰；页面长时间退到后台后结束登录，返回时重新确认。
6. 手机丢失时，只能在对应电脑本机移除该设备；现有登录立即失效，重新使用需再次本机配对。

## 已确认决策

- 宿主范围：公司电脑与家里电脑都要支持。
- 客户端范围：主要由用户自己的同一部手机访问两台宿主。
- 当前阶段只讨论和记录方案，不修改插件代码。
- 上游兼容策略：安全边界优先，危险访问模式直接删除，不为兼容现有行为而保留旁路；接受这可能降低破坏性改动 PR 的合并概率。
- 实施与贡献策略：允许重写为自己的安全分支，先自用验证；之后可提交代码 PR，也可只向上游提交完整 idea、威胁模型和实现方案，由开发者选择接受、部分采用或自行重写。
- 设计优先级：安全第一，方便第二。
- 手机端凭据：选择纯浏览器 Passkey/WebAuthn，不要求安装 WARP、Tailscale App 或客户端证书。
- 网络入口：删除独立 LAN 模式；公司内外统一走固定 HTTPS 公网入口，不保留普通 LAN HTTP、Host 分类、LAN 免密或 `0.0.0.0` 局域网监听。
- 身份模型：不建立用户名/密码账号系统，只做 Passkey/WebAuthn 凭据白名单；凭据可命名、查看和撤销。
- 凭据恢复：不提供远程密码、恢复码或邮箱找回；手机凭据丢失后，只能在对应宿主电脑的本机设置页重新配对。
- 宿主隔离：公司电脑与家里电脑分别注册独立 Passkey 凭据，不同步白名单、密钥或会话。
- 访问入口：手机分别保存“公司 DSH”和“家里 DSH”两个固定网址，不建立统一中转入口。
- 日常验证：页面保持打开期间不重复打扰；每次关闭后重新进入，都重新用指纹或面容确认，不提供 7 天或长期免验证登录；网页退到后台或手机锁屏超过 10 分钟后结束登录。
- 首次授权：电脑本机生成一次性二维码，手机扫码提出申请，电脑端显示申请后必须再手动确认“允许”才加入白名单；二维码本身不能直接授予权限。
- 固定网址配置：每台电脑由用户在 Cloudflare 建好固定网址并粘贴一次所需凭据；插件不负责 Cloudflare 账号登录或自动创建域名。
- 验证边界：插件自身维护和验证手机凭据白名单；Cloudflare 只提供固定 HTTPS 入口，不强制依赖 Cloudflare Access 账号登录。
- 本机管理：新增/删除手机、查看或修改公网入口凭据等安全设置只允许在宿主电脑本机操作。
- 凭据同步范围：允许获准登录凭据跟随同一 Apple/Google 账号同步到用户自己的其他设备；这些设备仍需完成各自的指纹、面容或锁屏密码确认，不要求严格限定唯一物理手机。
- 远程权限：手机验证通过后可以完整使用 DSH；新增/删除设备、修改公网入口、查看相关凭据等 Pocket 安全设置仍只允许在宿主电脑本机操作。
